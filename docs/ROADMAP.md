# ROADMAP — 多机 / 多人 / 多线演进路线图

> 现状基线：单机单线闭环已实战验证（见 PLAYBOOK）。
> 本路线图回答三个问题：远端发起方和人怎么进通道？多条任务线怎么并行？更多机器怎么加？
>
> 原则不变式（任何 Phase 都不得违反）：文件即状态 · 人只出现在裁决点 · 证据不可变 ·
> RUNBOOK 唯一事实源 · 渐进授权。

版本：v2（2026-10-04 并入 herdr/Omarchy 研究启示，见 STUDY.md）

## Phase 1 ✅ 已落地（单机单线闭环）

信箱协议 + 扫描器巡查 + RUNBOOK 状态机 + 监工代裁链 + TUI 观察窗 + 团队注册表。

## Phase 2（近期）：远端发起方与人类的通信自动化

**目标：消灭"人肉捎话"，发起方与监工直接对话，人只收升级通知。**

1. **指令下行（发起方 → 信箱）**
   - 方案 A（推荐）：发起方获**信箱限写权限**（仅任务信箱与报告信箱可写），拆完任务直接落盘，巡查 ≤10 分钟捕获。
   - 方案 B（备选）：发起方侧建 outbox 目录，定时推送到信箱并归档。
   - 验收：新指令从写完到被播报 ≤10 分钟，无需人复制粘贴。
2. **裁决上行（监工 → 发起方）**
   - 升级事件生成可直接粘贴的消息（包裹路径 + 结论 + 请裁事项）；
   - 中期：发起方侧守门脚本定时检查信箱，有 `need_cto` 标记才唤起处理。
   - 验收：发起方零巡检也能在 30 分钟内收到待审提醒。
3. **团队注册表**（✅ 已落地）：成员身份/启动方式/历史署名/资格边界，路由与资格自查查表化；多机阶段扩展为按 host 分片联合注册表。
4. **人类通知渠道**：`blocking` 级事件推即时通讯 webhook；`routine` 级攒日报。验收：人离开对话窗口也不会错过 blocking 事件超过 15 分钟。
5. **TUI 动作键**：选中包裹 `d` 派发 / `v` 复活 / `a` 批准 / `e` 升级，每个动作照旧留痕。前提：只读版信任期满且零误报。
6. **安装器**（启示见 STUDY/Omarchy）：`install.sh` 一条命令——建 $POSTA_HOME、装 tools、注册巡查、可选拉起 TUI。把 6 步手工 quickstart 压成 1 步。
7. **POSTA SKILL.md**（启示见 STUDY/herdr）：把信箱协议写成任何 agent 可领取的技能（像 herdr 的 agent skill file），领了即入伙——也是进入 herdr skills 生态的通道。

## Phase 3（中期）：双线与多任务并发

**目标：多任务同时在飞，资源不打架，人不当调度员。**

1. **资源登记与预约**：端口/容器/卷/环境谁占用谁预约；派发前必查，冲突排队或另配资源。
2. **优先级车道**：包裹带 `urgency: routine | need_decision | blocking`；routine 攒批省额度，blocking 即时唤醒。
3. **并发上限与预算**：登记表加 running 上限 + 每单预算；超限进队列。
4. **同候选互斥**：同一冻结产物上不并行两个验收任务，登记表自动检查。
5. **巡查与观察窗升级**：多 running 任务分组播报；任务面板分页/过滤。
6. **包裹已读/未读语义**（启示见 STUDY/herdr 五态模型）：done（完成但人未看）与 idle（已看）分开计数；待审队列只显示未读，去噪。
7. **按任务线 rollup**：观察窗状态条按任务线聚合（借鉴 herdr workspace rollup），一眼看出哪条线需要关注。
8. 验收：两线并行跑完整周期，零资源冲突，零漏播报。

## Phase 4（远期）：多电脑扩展

**目标：第 N 台机器即插即用，信箱全局一致。**

1. **信箱底座迁到 git 远端**：信箱即仓库，push/pull 即收发——天然多机一致、全历史、离线可用；发起方 push 权限即信箱写权限。
2. **机器登记表**：每台机器的角色（可跑哪些执行者、有哪些资源）、地址、额度。
3. **资格注册表多机化**：TEAM_ROSTER 按 host 分片联合；资格冲突自查全局查表。
4. **终端复用器的位置**：长时终端 worker 用 herdr 类工具管 pane（断线存活/随时围观）；监工仍走文件协议——进程层与协议层互不侵入。
5. **posta daemon 化**（启示见 STUDY/herdr server/client + Omarchy omarchy-shell）：巡查从 cron 迁为常驻守护服务，TUI/Web 作为一次性客户端 attach——观察与行动分离，事件即时推送而非轮询。
6. **统一看板**：Web 层（复用状态引擎）聚合所有机器的登记表与信箱摘要。
6. 验收：新机器从裸机到可领任务 ≤30 分钟，且无需人改 RUNBOOK。

## 人的角色演进（贯穿各 Phase）

| 阶段 | 人的动作 |
|---|---|
| 现在 | 转达终审、偶发代裁 |
| Phase 2 后 | 只收 blocking 通知 + 在监工台按键代裁 |
| Phase 3 后 | 只处理升级事件（新资源授权、冲突裁定、预算调整） |
| Phase 4 后 | 定义新任务的目标与边界，其余不碰 |

## 不做清单（防过度工程）

- 不做通用调度框架（任务形态单一：验收/补证/修复类）
- 不引入消息队列/数据库（git + 文件 + sqlite 够用）
- 不给弱模型加"判断"职责，除非白名单规则覆盖不了
- 不追求看板好看，先保证人裁决路径最短
